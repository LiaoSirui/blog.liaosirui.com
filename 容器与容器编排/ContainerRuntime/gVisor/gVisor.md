## gVisor 架构

gVisor 的架构里有两个核心角色。一个是 Sentry ，它是一个用 Go 写的、跑在用户态的内核实现，负责处理容器内进程发出的系统调用。容器里的进程发起 `read() `，这个调用不会直接进宿主内核，而是被 Sentry 接住，由它自己维护一套文件描述符表、内存管理、信号处理逻辑。

另一个是 Gofer ，负责文件系统的实际读写。Sentry 不直接碰宿主的文件系统，需要读文件时通过一套进程间通信协议把请求转给 Gofer，由 Gofer 在沙箱外完成实际的文件操作。这个设计是为了把文件访问的权限边界收得更紧。

这套架构带来的直接结果就是：容器内看到的 `/proc `、 `/sys `是模拟出来的， `uname `返回的内核版本是固定的（gVisor 模拟的版本号）， `dmesg `这类需要直接读内核环形缓冲区的操作基本都不可用。这不是 bug，是架构决定的。

有个细节值得注意：Sentry 拦截系统调用有两种实现方式，早期的 ptrace 方式性能损耗大，后来有了基于 KVM 的方式（需要 `/dev/kvm `可用），再后来主推的是 systrap 方式，靠 seccomp 加信号机制来拦截，不需要虚拟化支持。这意味着你在云主机、嵌套虚拟化的环境里也能跑起来，不强制要求 KVM。

## 最小验证

`runsc `自带一个 `do `子命令，可以在不经过任何容器编排的情况下直接跑一条命令在沙箱里，用来做最小验证非常合适：

```bash
runsc --network=none do uname -a
```
